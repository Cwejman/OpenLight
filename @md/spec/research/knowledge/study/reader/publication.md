# Publishing a repository as itself

The end this is built toward: a repository's own site is the repository, read through this surface, generated by its pipeline on every change. Not a site built beside the knowledge and kept in step by hand, which is the arrangement that rots. Held 2026-09-11, not begun.

## 1. The gate

It is not started until the thing is worth publishing, and [the path forward](forward.md#7-the-medium-beyond-the-page) holds the two judgments that decide it. Both are judgments rather than measurements, and neither has been made. What is worth repeating here is only the reason to wait: a published surface fixes a shape in place, and fixing the wrong one costs more than waiting for the right one.

## 2. What is digested, and what is not

A repository holds much that is not knowledge under the code: source, configuration, scaffolding, other people's files. So the substrate is not the whole tree. A file enters it by saying so, in frontmatter that stamps it as written under the code, and everything else stays a file the site does not read.

That rule pays twice. The surface stops guessing what is a brief, and a writer declares their intent where the intent belongs, in the file itself. It also makes the boundary visible: what a repository holds as knowledge is countable, and what it holds beside that is plainly other.

The stamp's exact form is open, and it belongs to [the practice](../10-comprehension/poc.md) rather than to this program, since it governs how knowledge is written and not how it is shown.

## 3. What the pipeline would do

Read the tree, keep the files that carry the stamp, emit the manifest the page needs, and publish the page beside it. The server this reader runs today reduces to those few lines, which is the whole of the gain being weighed: a build step earns its place only by removing a service, never by adding a pipeline.

# Clean-room pass: README against the ontology

Ground: `/Users/jcwejman/git/@x/night/README.md` (52 lines) and `/Users/jcwejman/git/@x/night/@md/spec/research/knowledge/study/08-win-driven/ontology.md`, read in that order, nothing else. README line numbers are given as `R<n>`; ontology entries by heading.

## 1. Contradictions

### 1.1 Medium: typed vs. nothing typed

- README R23: "Human, classical program, and model in one **typed, versioned medium** — that bridge does not exist today."
- README R15: "**Text is not data.** This is where the Unix lineage ends: text makes every program re-parse what the last one meant".
- README R23: "Prose leaves markdown for its native form".
- Ontology, Medium: "Is made of briefs and links, **nothing typed** — Both its readers, person and model, read prose. No schemas, no edge types; **markdown in directories is enough**, tracked in version control."

The same word carries opposite properties. The ontology tries to absorb this in Field ("The field is that medium once every holon has an address and a contract ... the README's word for it; medium, space and field are three words because they are three things"), i.e. it says the README's "medium" is the ontology's "field". But the README's "medium" sentence is the bridge claim of the whole entry, and the ontology's Medium entry names a technology (markdown, version control) while the preamble says "The knowledge words, comprehension down to prism, name no technology". Not reconciled: the README says markdown is left; the ontology says markdown is enough.

### 1.2 Contracts for models: typed vs. prose

- README R17: "A model is such a program: its context a **typed selection of the field**, its output **typed structure** back into it."
- README R19: "a model reads the **same contracts** a person composes with directly, in place".
- Ontology, Contract: "Is typed for the one citizen that cannot read a sentence — For the classical program, the contract is types. **For people and models, it is prose.**"
- Ontology, preamble: "Left out on purpose: ... **types and schemas**, which are for the one citizen that cannot read a sentence."
- Ontology, Program: "Its context a **selection of the medium**, its output landing back as structure."

The README's lever is that the model's context and output are typed. The ontology removes types from the model's side and, in Program, drops both "typed" and "field" (it says "medium", which it defines as untyped). Inside the ontology, Prism says the opposite of Program: "Is cut from the **field**". Contract also says "Lives in the medium it governs" while the Medium is "nothing typed" and the classical program's contract "is types" — a typed thing living in an untyped medium.

### 1.3 Harness: field vs. medium, and dissolved by what

- README R17: "that dissolves the harness as a separate technology — **the field** is a first-class harness to everything, every program a tool, every place a context, every run recorded".
- Ontology, Harness: "Is dissolved by the **citizen** — **The medium** is a first-class harness to everything, every program a tool, every place a context, every run recorded".

Two changes in one quoted sentence. (a) "field" becomes "medium", in a document whose Field entry insists "medium, space and field are three words because they are three things". (b) The README's dissolution follows from the substrate's fact (R15 "That one fact is the lever, and it moves three things", then R17 programs carrying their interface "as types in the field"); the ontology attributes it to the citizen. The README also keeps "harness" as a positive predicate of the field; the ontology's heading is "What a tool builds around a model to bound it. Retired."

### 1.4 Interface: stands on the mechanism vs. rests on no tenet

- README R43: "**The experience**, standing on the mechanism: `view.md` (components, mounts, the three selections, the glue)".
- README R41: "**The mechanism**, in dependency order — each file uses only what the ones before it define: `substrate.md` ... → `engine.md` ... → `chassis.md` ... → `sdk.md`".
- README R19: "**The interface builds on primitives, as data does.** ... Which components can draw a thing is a read of the field".
- Ontology, Interface: "Rests on the medium's law alone, on no tenet beneath — **Not on the engine, the substrate or any specific of OpenLight.** Briefs and links under a gradient are enough, which is why it can be built before the layers under it are settled."

The README's interface stands on substrate → engine → chassis → sdk and is "a read of the field". The ontology's interface rests on none of them and can be built first. This is also a build-order contradiction: README R29 "code follows the spec, the alignment of the built layer first" and R33 "to build, 4 and 5" (mechanism then experience); ontology Interface: "Building it is where the arc goes next."

### 1.5 Substrate: the lever vs. circuitry below the kernel

- README R15: "OpenLight's **substrate** is typed against itself — contracts are chunks in the same field they govern, every change a commit on a branch — so structure is what a program *receives*, never what it recovers. **That one fact is the lever**, and it moves three things".
- README R41: "`substrate.md` (the field's law: chunks, connections, types, boundaries) → `engine.md`".
- Ontology, Substrate: "Is circuitry that keeps, beside the processor that computes — Both sit below the kernel, and neither is it. The spec tree still holds the substrate as a tenet beside the engine; the ontology places it below the kernel".
- Ontology, Kernel: "Sits below the interface — Above it, where comprehension happens. **Below it, only circuitry**: what keeps and what computes."
- Ontology, Interface: "Where comprehension happens ... **Where technological progress now emanates from.**"

The essence sentences agree ("the law of laying it down, chunks, connections, types and boundaries, typed against itself, every change a commit on a branch" quotes the README). What changed is rank: README's substrate is the lever; the ontology's is "circuitry" under a kernel the README never names, and the lever moves to the interface. The ontology declares this drift itself, so it is a known split, but it is a contradiction with the entry as written.

### 1.6 Engine: the runtime vs. one citizen among many

- README R41: "`engine.md` (**running programs against it**: stores and attach, the call context, expressions, lifecycle, the protocol)".
- Ontology, Engine: "A contracted whole of something larger, with its own execution and mechanics, made interoperable through the substrate. **A citizen, not a tenet.**" / "Is a citizen, and there are many ... **none is the platform**." / "The spec tree still names it the engine, as if it were the only one; the ontology makes it one citizen among engines".
- Ontology, Kernel: "Is federated by contract — Kernels join by contract, one **attaching another's store**" — attach moves from engine to kernel.

Declared by the ontology. Two further points it does not declare:

- Attach's object. README R17: "attach a peer's **store** and its programs are usable at once." Ontology, Program: "Attach a peer's **kernel** and its programs compound with yours at once." Ontology, Kernel: "one attaching another's **store**". The ontology says both within itself.
- README R17: "A **program** — **the only unit of execution**, headless". Ontology, Engine: "with its own execution and mechanics" / "An engine executes" / "Each runs what it runs the way it runs it". If an engine executes with its own mechanics, the program is not the only unit of execution. Ontology, Program, keeps "The unit of execution" without "only".

### 1.7 Program and model: a model is a program vs. a program cannot comprehend

- README R17: "A model is such a program".
- Ontology, Knower: "the README says citizen, which includes programs, and **a program cannot comprehend**."
- Ontology, Knower, essence: "a person, or **a model in a session**."
- Ontology, Program: "Is a citizen, and **what a model is once it is one**."
- Ontology, Citizen: "A person and a model are citizens that know; a classical program ... is a citizen that only matches."

The ontology holds that a model is a knower (comprehends), that a model is a program, and that a program cannot comprehend. It rescues this by inserting "classical" in Citizen but not in Knower, where the sentence is used to reject the README's word.

### 1.8 Citizen: what the README said

- README R13, the only use: "**The monolith becomes a citizen.**"
- Ontology, Knower: "the README says citizen, which includes programs".

The README's citizen is the monolith — the model session — admitted to the field. It does not say citizen includes programs. The ontology's Citizen ("a person, a model, a program, or what draws a screen") is the ontology's widening, attributed to the README.

### 1.9 Trail: what a run read vs. what a brief is named by

- README R11: "the trail that produced it — **what was read, in what order, against which state** — is not addressable or reproducible."
- Ontology, Trail: "What leads to a brief: every brief that names it, and every change it has had. Never written, always derived." / "Runs the links backward".
- Ontology, Knower: "**A read changes the knower. A write changes the medium.**"
- Ontology, Program: "every **write** walks back to the program that made it and the person who ran it."

The README's trail is the record of a run, reads included. The ontology's trail is derived from links and commits — writes. Under Knower a read leaves nothing in the medium, so the ontology's trail cannot hold "what was read, in what order". Same word, different object.

### 1.10 Field keeps vs. substrate/kernel keep

- README R21: "**The field keeps everything.**"
- Ontology, Substrate: "What the field rests in and what outlives every kernel" / "**Holds the field at rest** — The disk and its format".
- Ontology, Trail: "The commits hold it; the **kernel keeps them**, and in the markdown practice git does."

In the README the field is the keeper; in the ontology the field is the kept thing and keeping belongs to substrate (at rest) and kernel (open).

### 1.11 Boundary: two senses in the README, one in the ontology

- README R7: "wherever insight fails to cross a **boundary**: between programs, between a person and their tools, between the roles of an organisation."
- README R21: "**boundaries** before a run, inspection during, history after."
- Ontology, Boundary: "A rule on acts over a region of the space: who may read there, who may write." / "Bounds a region of space, not a kind of thing".

The README's first boundary is the wall the project removes; its second is the one it keeps. The ontology defines only the second. Not a contradiction of meaning within the second sense, but the ontology's "the whole reason for the code" (Comprehension: "The friction of that meeting, across roles, backgrounds and processes") is the README's first sense with no word.

### 1.12 Branch dropped

- README R11 (the deficiency): "a linear transcript, append-only, nowhere to step back to, **no branch to take**".
- README R15 (the cure): "every change **a commit on a branch**".
- Ontology, Commit: "its address is its place in time, and **it stands on the commit before it**."

The ontology's commit is a line; the README's is on a branch, and the absence of branching is the README's first-named deficiency of the transcript.

### 1.13 Interface: two README senses, one ontology word

- README R17: "carries its **interface** in its body: what it takes and what it produces".
- README R19: "**The interface** builds on primitives".
- Ontology, Interface: "Where comprehension happens: the surface at which a citizen meets the medium."

The ontology takes the README's second sense and renames the first "contract". Not wrong, but the README still uses "interface" for what the ontology calls contract.

## 3. The three things

README R15: "That one fact is the lever, and it moves three things".

### 3.1 "Programs compound." (R17)

Carried by: **Program** ("Composes by matching, which is the amplifier in the technical arc — A call is matched, never parsed. Attach a peer's kernel and its programs compound with yours at once."), **Contract** ("so things meet by matching rather than by custom glue"), **Citizen** ("A citizen's output is ground the next citizen stands on"), **Harness** ("Is dissolved by the citizen").

Carried whole? **Mostly, minus the types.** What is carried: headless unit; contract in the body; matched not parsed; attach a peer's; output is the next one's ground; harness dissolved; "a model simply thrives in it" lands as Ground "a fresh session holds nothing, becomes what it reads". What is not: "as types in the field" (Contract makes the model's contract prose; Program says "selection of the medium", untyped); "the only unit of execution" (engines execute, 1.6); "every place a context" (no place word); the attach object (store vs kernel). The README's sentence is about types doing the matching; the ontology keeps the matching and drops the types.

### 3.2 "The interface builds on primitives, as data does." (R19)

Carried by: **Interface** (two relations), **Citizen** ("or what draws a screen"), **Contract** (matching rather than glue). The ontology repeats the README's closing sentence verbatim: Interface "Nobody has had the experience yet; it has to be built to be felt" / README "Nobody has had this experience yet; it has to be built to be felt."

Carried whole? **No — the thinnest of the three, and inverted.** Not carried: component; "the small family — prose, tables, lists, badges, buttons"; "Which components can draw a thing is a read of the field"; "a model reads the same contracts a person composes with directly, in place"; "The interface is not designed ahead of the data; it forms around what you are working with"; "the whole environment ... is field data"; "the walls between design tool, framework and running product fall". What the ontology carries instead is that the interface "Rests on the medium's law alone ... Not on the engine, the substrate or any specific of OpenLight" — the README's second thing is that the interface builds on the same typed primitives as data does; the ontology's interface builds on none of them. The sentence survives; the mechanism does not.

### 3.3 "The field keeps everything." (R21)

Carried by: **Commit** ("One write, kept: what changed, by whom, why, and in what order"), **Boundary** ("Boundaries before a run, inspection during, history after. Trust is native rather than bolted on, because every act is judged under one rule the kernel keeps"), **Trail** ("Carries history as well as reach"), **Kernel** ("Is the one thing every act goes through"), **Substrate** ("Holds the field at rest"), **Consolidation** ("can be made again from the same point and asked to give the same answer"), **Program** ("every write walks back to the program that made it and the person who ran it").

Carried whole? **Mostly, with the keeper moved and reads lost.** The "boundaries before a run, inspection during, history after" line and "Trust is native rather than bolted on" are quoted in Boundary. "the same lossless record is what lets the next reader, person or program or model, stand on exactly what the last one produced" lands as Consolidation. Not carried: the field as the keeper (Substrate and Kernel keep, 1.10); "bounded process" (no word); reads in the record (Trail is derived from writes; Knower "A read changes the knower. A write changes the medium." — 1.9); the branch (1.12); whether a Comment ("A write that stands on a brief without changing it") is a commit, given README "Every write is a commit".

## 4. Ontology words the README lacks

Ontology words in order: comprehension, knower, win, amplify, consolidation, brief, ground, link, trail, gradient, holon, word, medium, space, field, boundary, commit, comment, citizen, prism, interface, kernel, substrate, processor, contract, program, engine, specification, harness.

The README uses (some in other senses): medium, field, boundary, commit, citizen, interface, substrate, contract(s), program, engine, harness, trail (R11, other sense), link (R9, the web's), spec/specified (for specification), grounding (R47, R49; not "ground").

The README never uses: **comprehension, knower, win, amplify, consolidation, brief, ground (as a noun for what is stood on), gradient, holon, word, space, comment, prism, kernel, processor.**

Would the README gain?

- **kernel** — Yes, if the ontology's ruling stands. The README's mechanism order is "substrate → engine → chassis → sdk" and its runtime word is engine; the ontology has demoted engine to a citizen and put the kernel where the README has nothing. Either the README's R41 is wrong or the ontology's Kernel is. The README cannot stay silent on it.
- **space** — Yes. The README says "a point in a field" (R13), "every place a context" (R17), "addressable" (R13), and uses "field" for both the where and the what. The ontology's Field entry names the README's usage ("the README's word for it") and splits it; the README would read cleaner with the split.
- **prism** — Yes. README R17 "its context a typed selection of the field" is Prism's essence ("A selection, never the whole, and recomputed as the work moves"). Naming it would tie the model's context to the person's reading, which the README separately claims ("a model reads the same contracts a person composes with").
- **ground** — Yes. The README's "floor for the next one" (R7), "stand on" (R13, R17, R21), "stood on" (R7) are the ontology's ground; "a model simply thrives in it" is Ground's "becomes what it reads ... is the engineer or the planner by its ground alone", a sharper claim than the README's.
- **consolidation** — Yes. README R11's deficiency, "compression and handover happen only by inference over the text itself", is what Consolidation's "Makes inference deterministic, because the field has a point" answers; the README names the disease and not the cure's word.
- **comprehension / win** — Possibly. The README opens "Knowledge compounds by interconnection" and never says what knowledge is worth or what compounds. The ontology's "The one value the code measures everything by" would give R7 its unit. But the README is an entry, not a code, and "the why before the how" (R29) already implies the gradient.
- **knower** — No. The README's triad "person or program or model" (R21) and "Human, classical program, and model" (R23) is deliberate; knower splits it and the ontology itself marks the word "named for now, not settled".
- **amplify** — No. The README's "compound" does the job and is the older word; Amplify's "The code amplifies comprehension; it does not harness it" is a code-side slogan.
- **brief, gradient, holon, word** — No, in the text. The README is itself written as one (why first, detail below), which is the point; naming them in the entry would be the how before the why.
- **comment, processor** — No.
- **specification** — No; "specified" and "spec tree" (R29) suffice.

## 5. Verdict

The ontology reads as the same project in its knowledge half and a different project at its base. It quotes the README's sentences — completion from a point, boundaries before a run, the harness dissolved, "it has to be built to be felt" — and reattaches them to other words: field becomes medium, the lever moves from substrate to interface, engine becomes one citizen, a kernel appears that the README lacks. The drift is one direction: away from types. The README's one fact is that structure is typed; the ontology leaves types out on purpose, makes the model's contract prose, and says markdown is enough.

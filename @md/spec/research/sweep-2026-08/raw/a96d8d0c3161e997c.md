## TOPIC A — Datalog's revival, and where it landed

**1. Datomic (Nubank) — actively maintained, quietly.** Datomic Pro went free/Apache-2.0 in April 2023 (https://blog.datomic.com/2023/04/datomic-is-free.html), Cloud in June 2023 (https://blog.datomic.com/2023/06/datomic-cloud-is-free.html), Datomic Local Aug 2023. **Development is live:** Datomic Pro **1.0.7705, dated 2026/07/10** (https://docs.datomic.com/releases-pro.html; Client API 1.0.91, same date). *Grade: shipped-and-adopted.* But the **blog is nearly dead** — five posts since 2023, most recent "Datomic at Clojure/Conj 2025", **2026-01-21** (https://blog.datomic.com/2026/01/conj2025.html). That post is the best public scale evidence: Netflix's "A Decade on Datomic" (Davis Shepherd, Jonathan Indig) and Nubank's "Immutable Knowledge Databases" — but it carries **no numbers**. The hard number is independent: Jepsen's report on **Datomic Pro 1.0.7075, 2024-05-15** (https://jepsen.io/analyses/datomic-pro-1.0.7075) states Nubank serves "nearly 94 million users, processing an average of 2.3 billion user transactions per day," and concludes "We found no evidence of safety bugs in Datomic." *Grade: shipped-and-adopted, independently verified.* Note the vendor blog (https://blog.datomic.com/2024/05/Jepsen-tests-Datomic.html) restates this as 2.5bn/100M — **do not cite the vendor's rounded-up version**. Jepsen's one real finding: intra-transaction operations execute with **concurrent, not serial, semantics** — composing two individually-correct transaction functions can violate an invariant. That is a genuine, under-advertised sharp edge.

**Adoption outside Clojure: could not establish.** No evidence found of non-JVM/non-Clojure Datomic uptake. The "Datomic is used at Netflix and Nubank" claim is true but both are Clojure shops; Nubank *owns* Cognitect. Treat "Datomic has broad adoption" as **folklore**.

**2. XTDB — Datalog was dropped, and they stopped saying so.** Accurate release dates via GitHub API (fetched 2026-08-26): **v2.0.0 published 2025-06-12**; **v2.1.0 published 2025-12-01**; latest is **v2.2.0-rc1, 2026-08-06** (prerelease). The last 1.x release — the Datalog line — was **1.24.5, 2025-03-25**. *(Your prior suspect dates: `created_at` on GitHub releases is the **tag** date and can precede or follow publication; v2.0.0-beta4 has created=2024-12-11 but published=2024-12-09. Use `published_at`.)* Substantively: **Datalog is gone and unmentioned.** https://xtdb.com/ (fetched 2026-08-26) markets "SQL that remembers everything," Postgres wire compatibility, and "comprehensive audit over immutable data with **SQL:2011**" — zero mentions of Datalog or XTQL. The v2.0.0 release notes mention XTQL once, as an alternative for across-time queries; docs.xtdb.com still carries an XTQL section, so **XTQL is alive but demoted**. The v2.1.0 notes (2025-12-01) mention neither, and are entirely about multi-database attach and SQL. **The bitemporality survived; the query language did not.** *Grade: shipped-niche.* This is the single cleanest data point in the whole brief: a Datalog-first database rewrote itself around SQL:2011 and now hides the Datalog heritage.

**RelationalAI**: alive and all-in on Snowflake — Snowflake 2026 Telecom Product Partner of the Year (2026-06-02), Gartner MQ mention (2026-02-05), agentic decision-intelligence launch on Snowflake (2026-06-02), all at https://relational.ai/blog. Its language **Rel** is explicitly "grounded in Datalog and first-order logic" and won a **2026 SIGMOD Research Highlight** (post dated 2026-05-05) for the SIGMOD 2025 paper "Rel: A Programming Language for Relational Data," with a Leis/Neumann technical perspective. *Grade: paper-only-plus-shipped-niche* — real product, distributed via Snowflake Marketplace, but no independent adoption numbers. **Funding 2026: could not establish** (no funding posts on their blog).

**4. Polonius — the decisive verdict, and it is anti-Datalog.** The Rust borrow-checker rewrite **shipped on nightly 2026-08-06**, but **not the Datalog version**. Blog post **2026-08-04**, https://blog.rust-lang.org/2026/08/04/enabling-polonius-alpha-on-nightly/: the 2018 Datalog formulation accepted sound code NLL rejected, but was "considerably slower than NLL to the extent that using that implementation… was a non-starter"; the team instead built "a new formulation… that required minimal rearchitecture of the existing NLL implementation." Tracking issue rust-lang/rust#160456 (opened 2026-08-03) confirms "Enabled on nightly (starting nightly-2026-08-06)," stabilization targeted "prior to the end of the year," worst-case 2-3x compile regression. Crucially, rust-lang/rust#160588 (closed 2026-08-06) is literally titled *"add a test showing polonius alpha is not a subset of datalog polonius"* — the shipped checker has **different semantics** from the Datalog one. rust-lang/polonius itself has had **no substantive commit since 2025-06-06** (only a CI fix 2026-08-17). *Grade: the Datalog approach was announced, prototyped, and replaced.*

**Honest verdict.** Datalog is a **perennially-rediscovered niche that wins as an internal IR, never as a user-facing product surface.** Where it genuinely won: static program analysis (Soufflé and Semmle's .QL/CodeQL — Wikipedia's Datalog article documents both, plus LogicBlox in retail planning), and incremental view maintenance — where Materialize's commercial success came precisely from *hiding* differential dataflow behind SQL. Where it lost: every attempt to make Datalog the query language users type (XTDB dropped it; Cozo died; DDlog archived; Polonius replaced it). **Note also**: Wikipedia's own framing is that Datalog "is rarely used as a programming language" because it is not Turing-complete and lacks integers/strings, so all real systems use "substantial extensions" — i.e. nobody ships Datalog, they ship a dialect. **Practitioner retrospectives: could not establish** with WebSearch exhausted; the Rust blog post above is the closest thing to a credible, non-vendor post-mortem, and it is damning.

## TOPIC B — Versioning structure, not just rows

**1. Datomic accretion limits — documented by the vendor, and worse than the marketing.** https://docs.datomic.com/operation/excision.html: excision "puts a substantial burden on background indexing. Large excisions can trigger indexing jobs whose execution time is **proportional to the size of the entire database**, leading to back pressure and reduced write availability," with the guidance to "avoid excising more than a few thousand datoms at a time on a live system," and it "should never be used to correct erroneous data." Capacity docs (https://docs.datomic.com/operation/capacity.html): "expect every datom to be stored **at least 3 times**"; memory-index-max 512m; colocated databases require a process to hold "the **sum** of every database's memory index"; and the explicit admission that "a common modeling mistake is to assume that **everything** temporal belongs in Datomic," recommending `noHistory`. **Read that together: the accretion model's own documentation tells you to turn accretion off for most attributes and warns that GDPR erasure is an O(database) operation.** *Grade: shipped, with vendor-documented limits.* Independent critical writeups: **could not establish**.

**2. Dolt — thriving, and honest about schema merge being the hard part.** dolthub/dolt: **24,269 stars, pushed 2026-08-25**, releases v2.3.1 (2026-08-19), v2.3.0 (2026-08-13) — daily-cadence engineering. Product line has expanded to **Doltgres 1.0 (2026-08-06)**, DoltLite, and DumboDB. *Grade: shipped-and-adopted.* On merge semantics (https://www.dolthub.com/docs/sql-reference/version-control/merges): Dolt separates **data conflicts** (per-table `dolt_conflicts_$table` with base_/our_/their_ columns, resolvable row-by-row) from **schema conflicts** (`dolt_schema_conflicts` with base_schema/our_schema/their_schema). The key asymmetry: schema conflicts "**prevent the merge from completing**," and resolution via `dolt_conflicts_resolve()` with `--ours`/`--theirs` accepts "**the *entire* table from the chosen side**." **There is no cell-level merge for structure.** Dolt also surfaces `dolt_constraint_violations` for FK/unique breakage introduced by an otherwise-clean merge — the case where both sides are individually valid and the union is not. That is the real lesson. **Company funding/status 2026: could not establish** (no funding posts; blog names one engineer).

**3. Nessie is in maintenance; Iceberg won with tags, not branches.** projectnessie/nessie: 1,497 stars, pushed 2026-08-26, latest release **nessie-0.108.4, 2026-07-31** — looks healthy until you read the commit log. Of the ~200 most recent commits since 2026-01-01, **154 are `renovate[bot]`**; the largest human contributor is Robert Stupp with 33, and the rest are single-digit. *Grade: shipped-niche, effectively one-maintainer maintenance mode.* Meanwhile **Iceberg absorbed the use case**: https://raw.githubusercontent.com/apache/iceberg/main/format/spec.md (fetched 2026-08-26) states versions **1, 2 and 3 are "complete and adopted by the community"; v4 "under active development and has not been formally adopted."** Latest release apache-iceberg-**1.11.0, 2026-05-20**. Iceberg's branching doc (apache/iceberg `docs/docs/branching.md`) frames branches and tags as "named references to snapshots with their own independent lifecycles," and the documented workflows are **historical tags for audit/GDPR retention** and a **WAP audit branch** — and the audit branch is closed not by a merge but by `fastForward` of main to the branch head. **Iceberg has no branch merge.** So: what is actually used in production is snapshots + time travel + retention-bearing tags, plus fast-forward-only WAP branches. Real N-way branch/merge on a lake remains Nessie's pitch, and Nessie is coasting. *Grade for "git for data lakes": announced, then narrowed to tags.*

**4. Versioning a schema — the honest state of the art.** Three tiers, and only the boring one is load-bearing.

**TerminusDB** is the only system that genuinely models schema change as a first-class, branchable operation. https://terminusdb.org/docs/schema-migration-reference-guide/ and /docs/what-is-schema-weakening/ (both pages stamped "Published 6 Apr 2025 · Updated 30 Jul 2026", maintained by dfrnt.com; latest release **v12.0.7, 2026-08-10** — note this is *newer* than the v12.0.4/Feb-2026 in your brief). Its key concept: **weakening** — "a schema change is a *weakening* of the schema if the change can not possibly invalidate any data which was present in the original schema" (add optional property, add unrelated class, required→optional). Weakenings need no data migration; everything else needs an explicit, **replayable** migration script drawn from ~16 operations (`CreateClass`, `DeleteClass`, `MoveClass`, `UpcastClassProperty`, `CastClassProperty`, `ExpandEnum`, `ChangeKey`, …). Migrations "move schema and instance data together automatically in a replayable fashion," and can **target another branch's schema so migrations are re-performed to reach a common schema** — that is the closest thing to a genuine schema *merge* primitive anyone ships. Two operations, **`ChangeParents` and `ChangeCollection`, are unimplemented** — i.e. you cannot migrate the inheritance hierarchy, the most structural change there is. *Grade: shipped-niche, with the hardest case explicitly unimplemented.*

**Confluent Schema Registry** is the shipped-and-adopted version, and its lesson is precise (https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html). Default is **BACKWARD, and BACKWARD is non-transitive** — new schemas are checked "only against the latest schema," so a chain of pairwise-compatible changes can be **globally incompatible** (X-2 ↔ X may break while X-2↔X-1 and X-1↔X both pass). The Avro/Protobuf matrix: BW allows add-optional/remove-optional/remove-required/widen; FW allows add-optional/remove-optional/add-required/narrow; **FULL allows only add/remove optional fields**. And compatibility *is an upgrade-ordering contract, not a correctness one*: BACKWARD → "upgrade **all consumers** before you start producing new events"; FORWARD → upgrade producers first *and ensure old-schema data is no longer visible to consumers*; only **FULL/FULL_TRANSITIVE** lets producers and consumers upgrade independently. Kafka Streams supports only FULL/BACKWARD-family because it must also read old schemas from its own changelog. NONE means "create a brand-new topic and migrate."

**Buf** (https://buf.build/docs/breaking/rules/) is the same lesson at the type level: a strictness ladder FILE > PACKAGE > WIRE_JSON > WIRE, where FILE/PACKAGE guarantees are **language-dependent** and "don't account for custom code generation plugins," and wire checks **cannot reason about custom options** because "their effects are user-defined." **Avro** (https://avro.apache.org/docs/1.12.0/specification/) resolves record fields **by name, not position**, ignores writer fields absent from the reader, fills reader fields from defaults, and **errors** when a reader field has no default and no writer counterpart, or when an enum symbol is unknown with no enum default, or when no union branch matches.

**What this teaches.** A versioned contract can guarantee exactly one thing: **that a decode will not fail**, for a bounded set of syntactic changes, in a bounded direction, against a bounded set of prior versions. It cannot guarantee semantics (a field that changes meaning passes every check), cannot guarantee transitivity unless you pay for it explicitly and nobody does by default, cannot reason about anything user-extensible (Buf's custom options, generation plugins), and cannot survive a rename without an alias table. Structure merges only where the change lattice is a **join-semilattice** — TerminusDB's weakenings, Avro's field-name union, Confluent's FULL mode — and everywhere outside that lattice the shipped answer is uniformly the same: **stop, take one whole side (Dolt `--ours`/`--theirs`), fast-forward (Iceberg), or make a new topic/table and migrate (Confluent NONE).** Nobody merges structure. They serialize it.

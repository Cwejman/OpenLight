## TOPIC 1 — Empirical measures of documentation effectiveness

**Headline finding: the honest answer is "almost none."** Across SE research, technical communication, and information design I found a *handful* of true experiments in which documentation was the manipulated variable and a performance outcome was measured. Everything else — including the entire "documentation quality" literature — is survey, interview, artifact mining, or expert rating. All primary sources below retrieved 2026-08-26.

### The genuine exceptions (documentation manipulated, performance measured)

1. **Carroll, Smith-Kerker, Ford & Mazur-Rimetz, "The Minimal Manual", *Human-Computer Interaction* 3(2):123–153, 1987** — https://doi.org/10.1207/s15327051hci0302_2 (metadata via api.crossref.org; abstract reconstructed via api.openalex.org). Verbatim: *"In two experiments, the Minimal Manual was shown to afford more efficient learning progress than an otherwise comparable, commercially developed self-instruction manual, and was superior in the specific areas predicted by its design."* This is the strongest classical result: document *structure* manipulated, learning time and task success measured. Replication line: **Lazonder & van der Meij, "The minimal manual: is less really more?", *Int. J. Man-Machine Studies*, 1993** — https://doi.org/10.1006/imms.1993.1081. Grade: **paper-only** (but a real, replicated experimental programme; ~40 years old, hardware-manual domain).

2. **Mindermann & Wagner, "Usability and Security Effects of Code Examples on Crypto APIs", arXiv:1807.01095, 3 Jul 2018** — https://arxiv.org/abs/1807.01095. Verbatim: *"we created the open-source web platform CryptoExamples and conducted a controlled experiment where 58 students added symmetric encryption to a Java program… participants who used the platform were not only significantly more effective (+73 %) but also their code contained significantly less possible security vulnerabilities (-66 %)."* This is the cleanest modern documentation-as-treatment result I found. Grade: **paper-only**; n=58 students, single task, single API domain.

3. **Endrikat, Hanenberg, Robbes & Stefik, "How do API documentation and static typing affect API usability?", ICSE 2014, pp. 632–642** — https://doi.org/10.1145/2568225.2568299 (dblp `conf/icse/EndrikatHRS14`; 94 citations per Semantic Scholar). Abstract via OpenAlex: a controlled experiment plus exploratory study; *"the benefits of static typing are strengthened with explicit documentation, but… this was not as strongly felt with dynamically typed languages."* Design detail from Dan Luu's review, https://danluu.com/empirical-pl/: Java vs. a Dart/Groovy-style dynamic condition, subjects were students at a Java-teaching university, documentation was "free-form text plus examples", and **a single task deliberately chosen because both types and docs were expected to matter**. Grade: **paper-only**, and internally-validity-limited by the authors' own framing.

4. **Prechelt, Unger-Lamprecht, Philippsen & Tichy, "Two controlled experiments assessing the usefulness of design pattern documentation in program maintenance", *IEEE TSE* 28:595–606, 2002** — https://doi.org/10.1109/TSE.2002.1010061 (abstract via OpenAlex). Pattern comment lines added to *already well-commented* 360–560 LOC programs; *"a conservative analysis of results supports the hypothesis that pattern-relevant maintenance [tasks] were completed faster or with fewer errors if redundant pattern information was provided."* Notable because it isolates *marginal* documentation value. Grade: **paper-only**.

5. **Dekel & Herbsleb, "Improving API documentation usability with knowledge pushing", ICSE 2009** — https://doi.org/10.1109/ICSE.2009.5070532 (131 citations; abstract via OpenAlex). eMoose surfaced buried API *directives*; a lab study showed the awareness problem and benefit. Grade: **paper-only**; design details not verifiable without paywall access.

### Everything else in the canonical thread is self-report or artifact mining

- **Robillard & DeLine, "A field study of API learning obstacles", EMSE 16(6):703–732, 2011** — https://www.cs.mcgill.ca/~martin/papers/ese2011.pdf. Exact design from the PDF: Phase I survey **n=80** (8% of 1,000 randomly sampled Microsoft developers); Phase II **28 interviews** (+4 other stakeholders); Phase III follow-up survey **n=334** (17.3% of 1,936); ">440 professional developers" total. **No task-performance outcome anywhere.** The famous quote — *"The biggest hurdle when learning an API is the documentation"* — is one participant's opinion. Grade: **paper-only, descriptive**.
- **Uddin & Robillard, "How API documentation fails", *IEEE Software* 32(4):68–75, 2015** — https://www.cs.mcgill.ca/~martin/papers/ieeesw2015.pdf. Two surveys, **323 IBM professionals** (survey 1 n=69, 9.9%; survey 2 n=254, 23.8%). The "blockers" finding is self-rated severity, not measured blockage.
- **Aghajani et al., "Software Documentation Issues Unveiled", ICSE 2019** — https://doi.org/10.1109/ICSE.2019.00122; **878 documentation-related artifacts** mined from mailing lists, Stack Overflow, issue trackers, PRs → a taxonomy. **Aghajani et al., ICSE 2020** — https://doi.org/10.1145/3377811.3380405; *"two surveys performed with 146 practitioners."* Both: taxonomy/perception, no outcome.
- **Zhi et al., "Cost, benefits and quality of software development documentation: A systematic mapping", JSS 99:175–198, 2015** — https://doi.org/10.1016/j.jss.2014.09.042. Closed access; abstract elided by Elsevier at both Semantic Scholar and OpenAlex.
- **Treude, Middleton & Atapattu, "Beyond Accuracy: Assessing Software Documentation Quality", FSE 2020, arXiv:2007.10744** — 10 quality dimensions rated by technical editors. Measures *documents*, not developers.
- **Technical communication journals:** a Crossref sweep of *IEEE Transactions on Professional Communication* for manipulated-document-design experiments returned essentially nothing beyond the minimalism line (the closest hit, Watts 1990, https://doi.org/10.1109/47.49070, is a prototyping case report). Grade: **opinion/descriptive** dominates the field.

**No meta-analysis of documentation experiments exists** that I could locate via Crossref, arXiv, or OpenAlex.

## TOPIC 2 — ADRs, RFC culture, design docs

**Headline finding: zero outcome evidence.** Every artefact in this space is either a normative proposal, an adoption count, or a preference rating. Nothing links ADRs/RFCs/design docs to defects, delivery, decision quality, or onboarding time.

### ADRs
- **Nygard, "Documenting Architecture Decisions", 15 Nov 2011** — live at https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions. Its evidence is an experience report: the format had been used *"on a few of our projects since early August"* with 6–10 rotating developers. Grade: **opinion**.
- **ThoughtWorks Technology Radar, "Lightweight Architecture Decision Records"** — https://www.thoughtworks.com/radar/techniques/lightweight-architecture-decision-records. First appeared **Nov 2016 (Trial)**, Mar 2017 (Trial), **ADOPT in Nov 2017**, Adopt May 2018 (last edition featured). Grade: **opinion** (expert panel), no data.
- **Adoption, measured by me via GitHub API on 2026-08-26:** `joelparkerhenderson/architecture-decision-record` 16,736 stars / 2,799 forks; `npryce/adr-tools` 5,628 stars (last push 2024-04-25); `adr/madr` 2,420; `adr/adr.github.io` 437. GitHub code search: **3,576** files named `0001-record-architecture-decisions.md`; **6,096** `.md` files under a `doc/adr` path. Grade: **shipped-niche** — real but a four-digit footprint.
- **The one real study: Buchgeher, Schöberl, Geist, Dorninger, Haindl & Weinreich, "Using Architecture Decision Records in Open Source Projects — An MSR Study on GitHub", *IEEE Access*, 2023** — https://doi.org/10.1109/ACCESS.2023.3287654. Verbatim: *"the adoption of ADRs is still low… About 50% of all repositories with ADRs contain just one to five ADRs suggesting that the concept has been tried but not yet definitively adopted… In most repositories the template proposed by Michael Nygrad is used."* This is the decay signal you suspected — **half of adopters stop within five records**. It measures adoption, not benefit. Grade: **paper-only**.
- Corpus sizes from adjacent arXiv work: **980 ADRs across 109 GitHub repos** (Su et al., arXiv:2602.07609, 7 Feb 2026); **4,911 ADRs** (Dhar et al., DRAFT, arXiv:2504.08207, 11 Apr 2025).
- **Nogueira, Silva & Conte, "One Size Fits All? An Empirical Comparison of ADR Templates", arXiv:2604.27333, 30 Apr 2026** — DESMET FA expert screening then a controlled experiment with undergraduates; *"Nygard's template outperformed MADR in terms of the Overall Score."* This compares *templates* on comprehension/usability/ease-of-adoption constructs; it is not evidence ADRs improve any engineering outcome. Grade: **paper-only**.
- **Design rationale capture systematically fails:** Horner & Atwood, "Effective Design Rationale: Understanding the Barriers", in *Rationale Management in Software Engineering*, Springer 2006 — https://doi.org/10.1007/978-3-540-30998-7_3. Grade: **paper-only, analytic** (argument, not measurement).

### RFC culture
- **RFC 2026 / BCP 9, Bradner, "The Internet Standards Process — Revision 3", Oct 1996** — https://www.rfc-editor.org/rfc/rfc2026.txt. Its own stated warrant: *"the result of a number of years of evolution, driven… by experience."* **RFC 7282, Resnick, "On Consensus and Humming in the IETF", Jun 2014** — https://www.rfc-editor.org/rfc/rfc7282.html: *"rough consensus is achieved when all issues are addressed, but not necessarily accommodated"* — offers **no empirical evidence**. Grade: **opinion**.
- **The only quantitative study of RFC-style governance: Simcoe, "Standard Setting Committees: Consensus Governance for Shared Technology Platforms", *American Economic Review* 102(1):305–336, 2012** — https://doi.org/10.1257/aer.102.1.305. Uses IETF data; *"an observed slowdown in standards production between 1993 and 2003 can be linked to distributional conflicts created by the rapid commercialization of the Internet."* Note the direction: this measures the **cost** of consensus process, not its benefit. Grade: **paper-only** (top-tier, well cited).
- **Rust RFCs** (GitHub API, 2026-08-26): repo created 2014-03-07, 6,585 stars; **642 accepted RFC files** on `master`; **1,112 merged PRs, 933 closed-unmerged, 215 open** — i.e. ~46% of RFC pull requests close without merging, and rejected proposals outnumber accepted RFCs. Internal criticism is documented: "Up-votes instead of down-votes on RFCs" (internals.rust-lang.org t/6309, 2017-11-27) contains *"the RFC process is officially broken"*; "Thoughts on RFC/stabilization reform in 2019" (t/9202, mark-i-m, 2019-01-14) lists obsolete tracking pages, unreadable hundred-comment threads, acceptance being treated as a stabilization guarantee, shepherd burnout, and FCP momentum. Grade: **shipped-and-widely-adopted practice, opinion-level evidence**.
- **Python PEPs** (https://peps.python.org/api/peps.json, 2026-08-26): **738 PEPs** — 374 Final, 132 Rejected, 71 Withdrawn, 50 Draft, 39 Active, 36 Deferred, 25 Superseded, 11 Accepted; 580 Standards Track / 105 Informational / 53 Process. No outcome study exists.
- **Oxide RFDs:** RFD 1 "Requests for Discussion" (Frazelle & Cantrill, state Published) at https://rfd.shared.oxide.computer/rfd/0001; blog post https://oxide.computer/blog/rfd-1-requests-for-discussion, **Jessie Frazelle, 24 Jul 2020**. Justification is *"writing down ideas is important"*; **no metrics, no case studies**. Grade: **opinion**.
- **Malte Ubl, "Design Docs at Google", https://www.industrialempathy.com/posts/design-docs-at-google/, 6 Jul 2020** — a description of a cultural norm. Contains **no data, no study, no metric**. Grade: **opinion**.

## What I could not establish

- **Endrikat et al. 2014's n and effect sizes.** ACM DL returns 403 to both WebFetch and curl; no OA copy exists (OpenAlex: closed); the ACM author-izer link on Stefik's page (http://dl.acm.org/authorize?N87774) also 403s. For calibration, sibling experiments from the same lab used **n=27** (Mayer et al., OOPSLA 2012) and **n=20** (the type-names study), both quoted verbatim at https://danluu.com/empirical-pl/.
- **Buchgeher et al.'s exact repo/ADR counts and year-by-year adoption curve** — the gold-OA IEEE Access PDF returns 418/404 to every route I tried. Only the abstract's "about 50% have one to five ADRs" is verified.
- **Zhi et al. 2015's primary-study count and abstract** (Elsevier-closed; abstract elided at S2 and OpenAlex).
- **Per-experiment n for Prechelt et al. 2002, Dekel & Herbsleb 2009, Carroll et al. 1987, and Nogueira et al. 2026.** The often-repeated "~40% less learning time" for the Minimal Manual I could **not** trace to a primary source.
- **Any meta-analysis or pooled effect estimate for documentation.** None found.
- **Any study — of any design — linking ADRs, RFCs, or design docs to a downstream engineering outcome.** I am confident this does not exist as of 2026-08-26.
- Method caveat: this session's WebSearch budget (200 calls) was already exhausted before I started, so everything above came from direct fetches of Crossref, OpenAlex, Semantic Scholar, arXiv, dblp, the GitHub API, and primary web pages; Google Scholar, DuckDuckGo (CAPTCHA), Mojeek (403), ACM DL, IEEE Xplore, ResearchGate, and research.utwente.nl were all unreachable.

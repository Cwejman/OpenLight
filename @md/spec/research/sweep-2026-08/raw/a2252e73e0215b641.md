## Notion

**Mechanism.** Two separate systems. Page content is a uniform typed tree of *blocks*; database rows carry *properties*. In API version `2025-09-03` (changelog dated **2025-08-26**) Notion split the old `database` into a **database** (container) and **data sources** (tables) — the database object now returns only `data_sources: [{id, name}]`, and `properties` moved onto the data source. This is a real schema-layer improvement (multi-source databases), and it was a forced migration, so: **shipped-and-adopted**.

**Views.** Your prior is now out of date. Notion shipped a **Views API on 2026-03-19** — "Eight new endpoints let integrations programmatically manage database views." The `view` object exposes `object`, `id`, `parent`, `data_source_id`, `name`, `type`, `filter`, `sorts`, and `configuration`, documented as "View-specific layout configuration, **discriminated by `type`**." That last clause is the wall: `type` is a closed list of exactly ten — `table`, `board`, `calendar`, `timeline`, `gallery`, `list`, `form`, `chart`, `map`, `dashboard`. A view is a *preset selected from an enum*, and its config is a union branch keyed by that enum. Grade: **shipped**, adoption unknown (5 months old).

**Block layout.** Page layout *is* addressable — `column_list`/`column` with width ratios — but block `type` is likewise closed: 32 types, and the docs state plainly "The API does not support all block types... Only the block type objects listed in the reference below are supported," with unknown types degrading to `"unsupported"`. No plugin/component API, no user-defined property types. The nearest escape hatch is **interactive HTML blocks**, shipped in **Notion 3.6 (2026-07-01)** — but that is a sandboxed iframe the user places, not a renderer that declares what it accepts. Agent APIs went **public beta 2026-08-20**.

## Airtable

**Mechanism.** `FieldType` is a TypeScript enum in the SDK source with **33 members** — `'singleLineText' … 'button'`, `'externalSyncSource'`, `'aiText'`. Closed. Field-type extensibility was never shipped; I found no trace of it in the SDK or its issue tracker.

**The Blocks/Extensions SDK** is the most serious component API of the four, and deserves the credit: it is genuine React over live typed data (`useBase`, `useRecords`, `useLoadable`, `GlobalConfig` for persisted extension settings, `Field`/`Table`/`View` models). But note what an extension *declares*: nothing about types. It is not a declaration of "I accept records of shape X" — it is a mounted app that discovers `field.type` at runtime and branches. The match is imperative, not a query. And `ViewType` is closed at six in the SDK — `GRID, FORM, CALENDAR, GALLERY, KANBAN, BLOCK` (the Web API lists seven, adding `timeline`; the meaning of `block` there is documented inconsistently — **flagging as unverified**). `BLOCK` is the closest anyone gets to a third-party renderer occupying a view slot, but the user places it; it does not bid.

**Grade: shipped-niche, effectively frozen.** `Airtable/blocks` has 272 stars, and every 2026 commit I could see is Dependabot.

**Interface Designer is opaque.** `GET /v0/meta/bases/{baseId}/tables` returns per view only `id`, `type`, `name`, `personalForUserId`, `visibleFieldIds` — **no filters, grouping, or layout**, and Interfaces appear nowhere in the Web API. Layouts are not data. Verified 2025-06-24 repositioning: "The AI-Native Airtable Has Arrived," AI App Building + AI Agents. **I could not verify a product named "Omni"** in Airtable's newsroom — treat that name as unconfirmed.

## Tana

**Mechanism.** "Nodes are the only primitive" largely holds. A **supertag** carries **fields** ("attributes that describe the object that the supertag represents") plus a **content template** — "Every time you apply the supertag to a node, this template gets applied" — which may itself contain default values, plain nodes, *and search nodes*. Display config lives on the supertag: **pinned fields**, **"Build title from fields"** (a title expression over field values), "Show as checkbox". That title-expression mechanism is the closest shipped thing to your "template with expressions over the mounting call's arguments" — but it computes a *string*, not a subtree.

**Search nodes** are live queries that are themselves nodes in the graph (2500-result cap), and views attach to "all nodes that have children, including search nodes" — so a view is roughly node-attached config. But the view vocabulary is again fixed: **Outline, Table, Cards** plus **List, Calendar, Side menu, Tabs**. No user-defined view type; no renderer registry. **Grade: shipped-niche** — small; I could not verify current adoption or funding numbers, so I'm asserting none.

## Anytype

This is the crux, and the protobuf answers it flatly. From `pkg/lib/pb/model/protos/models.proto` (branch `develop`, fetched 2026-08-26):

- `enum RelationFormat` — **closed, 15 values**: `longtext, shorttext, number, status, tag, date, file, checkbox, url, email, phone, emoji, object, relations, map`.
- `enum ObjectType.Layout` — **closed, 28 values**: `basic, profile, todo, set, objectType, relation, file, dashboard, image, note, space, bookmark, …, discussion`.
- `Block.Content.Dataview.View.Type` — **closed, 6 values**: `Table, List, Gallery, Kanban, Calendar, Graph`.

So: **layout is a fixed enum.** Your suspicion is correct, and this is the sharpest disconfirmation available. What *is* object-like is impressive — `SmartBlockType` includes `Template = 0x120`, `STType = 0x210`, `STRelation = 0x209`, so templates, types, and relations are all genuinely objects in the same store, and `Dataview.View` carries `defaultTemplateId` and `defaultObjectTypeId` per view. Anytype got furthest on "schema and template are data." It got zero distance on "renderer is data." **Grade: shipped-niche, open source** (`anytype-heart`, 413 stars, pushed 2026-08-24).

## Cross-cutting: hypothesis confirmed, and stronger than stated

All four have an extensible **instance** schema — you may add types/supertags/tables and add properties/relations/fields to them. All four have a **closed set of view kinds**: 10 (Notion), 6–7 (Airtable), 7 (Tana), 6 dataview + 28 object layouts (Anytype). None lets a third party register a renderer that *bids* to render a type.

Two refinements your hypothesis understates. First, the closure is one level deeper than views: **no one lets you define a new property type either** — `RelationFormat` and `FieldType` are enums in the protocol, not records in the store. Extensibility stops at instances of a fixed vocabulary in both dimensions. Second, view *configuration* is everywhere a union discriminated by the view-kind enum — Notion's `configuration` "discriminated by `type`", Anytype's `View` message with `coverRelationKey`/`cardSize`/`groupRelationKey` fields that are meaningful only for particular `Type` values. That is the structural tell: config keyed by a closed tag is precisely what a *declaration-and-call* model replaces. The two partial counterexamples — Airtable's `ViewType.BLOCK` and Notion's interactive HTML blocks — are both user-placed sandboxes, not type-matched mounts, which is the distinction your model turns on.

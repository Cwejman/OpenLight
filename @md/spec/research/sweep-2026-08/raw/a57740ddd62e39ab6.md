## 1. HEADLINE

- **Five independent teams hit the same wall and invented the same fix, none of them the one the project proposes.** Uber, Plaid, DoorDash, Lyft and Shopify all converged on a *capability negotiation*: the client tells the server which component types it can render, and the server refuses to send anything else. Nobody solved shipping-a-new-component-to-an-old-client. Plaid's spec says it flatly: adding a new pane kind is a **major** version bump "which require[s] a client SDK upgrade."
- **The escape hatch is not an edge case — it is a named architectural tier.** Lyft's "Semantic Components" exist explicitly as "an escape hatch from server-driven land"; DoorDash has an untyped `custom` protobuf `Struct`. Both teams report the boundary eroding: DoorDash's "one pitfall we kept running into was gating the usage of `custom`"; Lyft's "sometimes the dividing line between semantic and declarative can be hazy."
- **Everyone's dispatch is a pinned key, not a query.** Airbnb's `SectionComponentType`, DoorDash's `FacetFactory`, Plaid's `oneof` pane type. A renderer *registry* is universal; a renderer *bid* ("which component can draw this?") is not shipped anywhere at scale. Anytype's protobuf settles the same question for the product tier: `RelationFormat` (15), `ObjectType.Layout` (28), `Dataview.View.Type` (6) are all closed enums.
- **Uber's Screenflow is the closest anyone came to the project's exact model — and it is a shutdown.** A DSL that was a restricted subset of TypeScript, only components as top-level definitions, restricted expressions in `render`, compiled to an IR, with `.d.sdl` definition files carrying types *and default values* so native could codegen matching protocols. Its versioning answer: CI recompiled every screen against *every previously shipped runtime version*. After ~2 years: "at least 16 flows" in production. The department was shut down in July 2020.
- **The generative-UI protocol race is over and the winner is opaque.** MCP Apps (SEP-1865) reached **Stable on 2026-01-26**; OpenAI's Apps SDK and MCP-UI both folded into it. `@modelcontextprotocol/ext-apps` did **12,177,761 downloads** in the last month. The unit is a sandboxed HTML iframe with no props schema — the opposite of a typed mount.
- **The low-code market is bifurcating, and Retool's June 2026 reversal is the datum that matters.** Retool abandoned its proprietary visual abstraction for React/TypeScript because the abstraction "prevented LLMs from working fluently." Airtable sold to Bending Spoons for $1.28B on ~$480M ARR after an ~$11.7B peak. Meanwhile Lovable reached $500M ARR and Appian grew 19%.
- **The 2021 Airbnb comment section already contained the strongest objection.** "Wow! You created a stripped down version of HTML" — and the top technical reply named coupling, caching, animation, platform-specific features, and "doing UI in gql schemas is awful."

## 2. SERVER-DRIVEN UI: WHAT IT COST

**The canonical design.** Airbnb's Ghost Platform ([Ryan Brooks, 29 Jun 2021](https://medium.com/airbnb-engineering/a-deep-dive-into-airbnbs-server-driven-ui-system-842244c5f5)) is *shipped-and-adopted*: "a majority of Airbnb's most used features (e.g. search, listing pages, checkout) are built on GP." Its shape maps almost term-for-term onto the project's claim. Sections are "a union of all possible section types. Each section type specifies the fields they provide" — a declaration of what it accepts. `SectionComponentType` "controls how a section's data model is rendered... enables one data model to be rendered in many different ways." `ILayout` is an interface whose implementations specify placements; each "has a unique renderer in each client's GP framework," and the framework "finds the proper section component to render that section."

Two things GP does *not* do, and both are the project's core claims. Dispatch is by an explicit pinned discriminator, not a query over the data — the server names the renderer. And layouts are a closed set with native renderers per client; a layout cannot be authored as data. GP's stated roadmap in 2021 was "nested sections," "improving discoverability of elements... through our design tools, such as Figma, and WYSIWYG editing of sections and placements, enabling no-code feature changes." That is the project's thesis listed as future work five years ago; I found no evidence it shipped.

**Failure mode 1 — versioning across clients you cannot force to upgrade.** This is where the record is richest and least flattering.

*Plaid Link / Flex Link* ([plaid.com, May 2021](https://plaid.com/blog/a-new-architecture-for-plaid-link-server-driven-ui-with-directed-graphs), *shipped-and-adopted*) is the sharpest statement. Workflows are versioned `experience.variant.major.minor.patch`, and: "**major**: ...incremented for breaking and incompatible changes which require a client SDK upgrade. e.g. Adding a new kind of pane." Explicitly: "The system supports a pre-defined number of pane nodes that all SDKs know how to render... New panes can be added as needed over time, but require an SDK update to render them with native platform UI." Their mitigation is pinning: "we maintain support for legacy SDK versions by pinning those to certain graph versions." So the promised benefit — ship UI without a release — holds only *within* the vocabulary already shipped. New vocabulary costs a release, plus indefinite maintenance of a frozen graph per stranded SDK generation.

*DoorDash Facets* ([24 Aug 2021](https://doordash.engineering/2021/08/24/improving-development-velocity-with-generic-server-driven-ui-components/), *shipped-and-adopted*) documents the sharp edges. "If we created a new version of an instrumental component, such as the store row in the homepage, and it was different enough that it warranted a new Facet ID, older versions of the app would omit those views as soon as the backend starts sending the newly versioned ones." A subtler one: "clients might understand the component, but a new action type might be unsupported, in which case the component will cause an error on action, but might still be rendered." Their fix: "a simple Semantic Versioning-based system that allowed clients to specify the extent of their Facet rendering capabilities... while making a call to the backend," plus client-side validation — "these two simple checks reduced our need to version our libraries by about 50%."

Then the finding that contradicts the obvious design: **"Fallback components were unnecessary."** They built prototypical fallback views per component Category out of fear, and "have not found this to be useful at all, as when we version components, we typically have a very specific, new design in mind." Shopify's Shop app went the other way — "the client would define a default layout for each section, and this default layout would be rendered if the client receives a new layout type it does not understand" ([22 Nov 2022](https://shopify.engineering/server-driven-ui-in-shop-app)). Two shipped systems, opposite conclusions. The reconciling read: a generic fallback is only useful when the new component is a *variation*; when it is genuinely new, degradation is worse than omission, and capability negotiation dominates.

*Lyft* ([Alex Hartwell, Mar 2023](https://eng.lyft.com/the-journey-to-server-driven-ui-at-lyft-bikes-and-scooters-c19264a0378e)) independently landed on the same name: cross-team alignment "started small with aligning on solutions to common problems like 'Capabilities' (which components are supported in which client versions)."

*Uber Screenflow* ([Artem Tyurin, Feb 2021](https://artem-tyurin.medium.com/screenflow-an-unfinished-attempt-at-a-cross-platform-server-driven-ui-at-uber-749c1bc1d89), *abandoned*) states the hazard most precisely: "With server-driven UI you get a very different cadence of releases for different parts... the older runtime could fetch a recently updated screen. That meant that without proper safety, a call to a non-existent API will cause a runtime crash." Their answer is the most rigorous anyone attempted and worth copying: "All definitions were versioned and every screen had to specify a version. When pushing screen changes to the monorepo, the CI invoked the compiler on all previous versions to ensure that the screen would run on all existing runtimes." That is the project's "mount is a call validated by the matching rule," extended over time: validate every call site against every shipped signature set. It is the correct answer and it costs a compiler, a monorepo, and a build matrix.

Two deserialization traps are worth flagging because they are silent. DoorDash: "our response format was a heterogeneous array containing different components... prone to deserialization errors." And concretely, SwiftProtobuf "would fail if a new enum case is returned in the response... we decided to migrate off of using SwiftProtobuf." A closed-world serializer plus an open-world component vocabulary is a crash.

**Failure mode 2 — the escape hatch.** Lyft names it: Semantic Components "can act as an escape hatch from server-driven land," introduced because "Declarative Components are powerful but come with a lot of limitations. It's hard to model complex animations and view hierarchies from the server... don't support highly responsive (i.e. fully client-side) interactions." And then: "Sometimes the dividing line between semantic and declarative can be hazy." DoorDash's version is an untyped `custom` field: "having a dynamic object is great for flexibility, [but] there are downsides caused by the lack of type-safety and the potential for deserialization errors." Their recovery is instructive — "we started matching styling types with our design language system library, which has helped mitigate our usage of `custom`." The escape hatch shrinks when the design system becomes a typed vocabulary. That is a direct endorsement of the project's direction, arrived at by attrition.

**Failure mode 3 — performance and query-language mismatch.** DoorDash on the web: "The Facet data model was designed to be recursive... there was no clear way to understand how many nodes were presented in the data or if nodes had any children prior to requesting the data. This structure makes the process of requesting Facet data via GraphQL close to impossible or at the best case scenario inefficient." They flatten server-side and reconstruct client-side. Recursive component trees and field-selection query languages are structurally opposed. Airbnb sidestepped this by keeping sections *flat* — placements point at a top-level `sections` array by id — and listing nesting as future work. If the project's templates are trees of mounts, this is the constraint to design against early.

The 2021 HN thread carries the practitioner critique ([id 27707423](https://news.ycombinator.com/item?id=27707423)): "difficulty caching resulting in bad performance"; "you end up unnecessarily reloading entire screens just in case one small piece of UI changed"; "difficulty handling animations or smooth transitions"; "sdui+gql are opposite goals, sdui wants dumber clients gql wants smarter clients... you're basically sending your entire UI layout and receiving it back filled with data."

**Failure mode 4 — organizational coupling and registry fragmentation.** Same thread: "we prefer decoupled systems with clear interfaces and boundaries. SDUI is the opposite of that, it's tight coupling between all the clients and the backend, changes to your UI are split across a bunch of teams." Shopify's intern post shows the mechanism: faced with reusing another team's SDUI components, "we made the decision to create our own Shop Store components when needed, since this would allow us to control the data types in each section." A shared registry that a team cannot evolve gets forked. Lyft admits the endpoint: "We don't have a single framework to build SDUI at Lyft yet. Instead, feature teams have had a lot of freedom to experiment on their own."

**Failure mode 5 — designer workflow, mostly unsolved.** Airbnb's Figma/WYSIWYG ambition was roadmap. Uber got furthest: a browser-based IDE with live previews on all platforms, an intern-built time-travelling debugger enabled by immutable state, preview components supplying mock data, and "a tool that produces the UI in our language directly from Figma designs" — and notes "as with tools like Figma, browser-based experience allowed us to quickly share the progress between designers, developers, and product managers." That is the wall falling, and it died with the org.

**Abandonment evidence.** Spotify's HubFramework is archived, "DEPRECATED – Spotify's component-driven UI framework for iOS," last pushed 2018-11-06, 1,889 stars. Nubank/Zup's Beagle and Nimbus are *gone*: the `ZupIT` GitHub org now contains **3** repos, all Horusec; only third-party forks of Beagle survive, last pushed 2020–21. Counter-evidence that the pattern is alive: Yandex's **DivKit** has 2,664 stars and was pushed 2026-08-26. Shopify's Remote DOM (née remote-ui) is *shipped-and-adopted*: `@remote-dom/core` v1.11.1, **627,451 downloads last month**, repo pushed 2026-08-26, with the July 2025 note that the DOM-based extension system has begun rolling out. Remote DOM is the strongest existing implementation of "a mount is a call the host resolves": a "controller (that maps remote components to their native implementations)" over a message channel, with hosts in JavaScript, Kotlin *and* Swift.

## 3. THE LOW-CODE RECKONING

The honest reading is bifurcation with one real casualty class, not extinction.

Distress is concentrated in the *proprietary visual runtime sold to prosumers and agencies*. Airtable sold to Bending Spoons for **$1.28B cash** ([TechCrunch, 4 Aug 2026](https://techcrunch.com/2026/08/04/bending-spoons-to-buy-airtable-for-1-28b/)) on ~$480M ARR, after a 2021 peak above $11B; secondaries had it near $4B by January 2026. Wix cut ~20% of staff (~1,000 people) in a June 2026 SEC filing, naming "a more pronounced slowdown... in the growth of our **Partners** business" — the agencies. Pegasystems told the SEC on 21 Jul 2026: "Unprecedented changes in the AI market caused clients to delay their purchasing decisions. As a result, our ACV growth rate significantly slowed" — H1-26 revenue **down 1%**.

But governed enterprise automation is fine: Appian Q2-26 revenue **$203.3M, +19%**, cloud subscriptions +23%, net ARR expansion 115% — and its own boilerplate now says "process automation technology," the words "low-code" deleted. Pega Cloud ACV still grew 22%. And the market relocated rather than vanished: Lovable went $100M ARR (Jul 2025) → **$500M (Jun 2026)**, raising $400M at $13.3B on 12 Aug 2026; Replit went to a $9B valuation in March 2026.

The load-bearing datum for this project is **Retool's June 2026 reversal** ([17 Jun 2026](https://retool.com/blog/retool-launches-react-ai-app-builder)): it relaunched on React + TypeScript, saying its own abstractions were a liability that "prevented LLMs from working fluently," and repositioned as the governance/permissions layer that *imports* apps vibe-coded elsewhere. Read precisely, that is not a verdict against derivation. It is a verdict against **closed, non-inspectable** derivation. Every survivor's remaining moat is typed contracts — data access rules, permission inheritance, schema. The implication for this project is a constraint, not a refutation: the contracts are the asset; the artefact the derivation emits must be inspectable, and the renderer must not be a walled garden.

## 4. THE GENERATIVE-UI PROTOCOL RACE

Consolidation happened, inside MCP. **MCP Apps / SEP-1865** — "MCP Apps: Interactive User Interfaces for MCP," Track: Extensions, **Status: Stable (2026-01-26)**, created 2025-11-21 — is the standard. I verified the spec text directly. Its motivation section names the merger: MCP-UI "developed the bi-directional communication model," OpenAI's Apps SDK "further validated the demand," and this SEP "unifies the approaches pioneered by MCP-UI and the Apps SDK into a single, open standard." Extension identifier `io.modelcontextprotocol/ui`. Contract: a resource at a `ui://` URI with mimeType `text/html;profile=mcp-app`, linked from a tool via `_meta.ui.resourceUri`, rendered in a mandatory sandboxed iframe, with JSON-RPC over postMessage (`ui/initialize`, `ui/notifications/tool-result`, `ui/request-display-mode`) and declarative security via `_meta.ui.csp`. `@modelcontextprotocol/ext-apps` recorded **12,177,761 downloads** in the month to 2026-08-24 — verified against the npm API. Eleven hosts in the official client matrix, including ChatGPT, Claude, VS Code Copilot, Microsoft 365 Copilot, Goose, Postman, Cursor.

OpenAI's Apps SDK is now subordinate: its docs say "ChatGPT implements the open MCP Apps standard," with `_meta["openai/outputTemplate"]` and `window.openai` retained as compatibility aliases. MCP-UI moved to `MCP-UI-Org/mcp-ui` and states "the `@mcp-ui/*` packages implement the MCP Apps standard." AG-UI (15,553 stars, `@ag-ui/core` ~6.08M downloads/month) is a transport — its event taxonomy contains **no UI-rendering events**. Vercel's RSC generative UI retreated: `@ai-sdk/rsc` is ~341k downloads/month against `ai`'s ~86.4M, and the docs warn "AI SDK RSC is currently experimental. We recommend using AI SDK UI for production."

**The decisive fact for this project: the winning unit is opaque.** An HTML/JS blob in an iframe, no props schema, data arriving by notification. Structured, typed component trees lost at the protocol layer and are thriving one layer up — Thesys renamed `crayon` to **`thesysdev/openui`** (8,459 stars, MIT, pushed 2026-08-26), whose **OpenUI Lang** parses a compact streaming DSL into a typed element tree validated against a JSON schema *generated from your component library*, which also generates the system prompt. `@openuidev/lang-core` was created 2026-03-25 and already does ~414k downloads/month.

That split is good news, not bad. The opaque standard fixes the transport and says nothing about authoring. A project whose interface is already typed data can emit into a `ui://` bundle *or* into a host's own components without rewriting; the commoditised asset is the hand-written iframe widget. The right posture is: ship the typed layer, treat MCP Apps as one adapter.

## 5. THE PRODUCT VIEW LAYERS

All four have an extensible *instance* schema and a **closed set of view kinds**. Nobody lets a third party register a renderer that bids to render a type.

**Notion** shipped a Views API on **2026-03-19** (eight endpoints), and split `database` into database + data sources in API version `2025-09-03`. But the `view` object's `configuration` is documented as "View-specific layout configuration, **discriminated by `type`**," where `type` is exactly ten values (`table`, `board`, `calendar`, `timeline`, `gallery`, `list`, `form`, `chart`, `map`, `dashboard`). Block types number 32 and unknown ones degrade to `"unsupported"`. No user-defined property types. Interactive HTML blocks (Notion 3.6, 2026-07-01) are a user-placed sandbox, not a type-matched mount.

**Airtable**'s `FieldType` is a 33-member TypeScript enum; field-type extensibility never shipped. The Blocks/Extensions SDK is the most serious component API of the four — real React over live typed data (`useBase`, `useRecords`, `GlobalConfig`) — but an extension declares *nothing* about types: it discovers `field.type` at runtime and branches. The match is imperative, not a query. `ViewType` is closed at six in the SDK. Interface Designer layouts are absent from the Web API entirely; `list views` returns only `id`, `type`, `name`, `visibleFieldIds`. `Airtable/blocks` has 272 stars and 2026 commits are Dependabot.

**Tana** comes closest on templates: a supertag carries fields plus a content template — "Every time you apply the supertag to a node, this template gets applied" — and "Build title from fields" is a title *expression over field values*. That is the project's "expressions over the mounting call's argument," except it computes a string, not a subtree. Views are Outline/Table/Cards/List/Calendar/Side menu/Tabs. *Shipped-niche.*

**Anytype** is the crux, and its protobuf answers flatly. In `pkg/lib/pb/model/protos/models.proto` (branch `develop`, read 2026-08-26): `RelationFormat` is a closed 15-value enum, `ObjectType.Layout` a closed 28-value enum, `Block.Content.Dataview.View.Type` a closed 6-value enum. Schema and templates genuinely are objects in the same store (`SmartBlockType` includes `Template`, `STType`, `STRelation`). Renderers are not. Anytype got furthest on "schema and template are data" and zero distance on "renderer is data."

The recurring limit is one level deeper than views: **no one lets you define a new property type either**. `RelationFormat` and `FieldType` are enums in the protocol, not records in the store. And view configuration is everywhere a union discriminated by the view-kind tag — which is precisely the shape a declaration-and-call model replaces.

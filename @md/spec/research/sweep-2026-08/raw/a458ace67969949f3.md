# (A) Schema-driven UI: the honest state

**Method note:** WebSearch quota for this session was exhausted before I began, so everything below comes from direct fetches of primary sources (GitHub API, npm registry API, raw source files, spec documents, HN Firebase/Algolia APIs) on **2026-08-26**. That skews evidence toward source code and issue trackers and away from blog-post opinion; where I have no primary evidence I say so.

## JSON Forms (EclipseSource) — shipped-niche, actively maintained

2,733 stars, v3.8.0 (2026-06-16), 147 open issues, `@jsonforms/core` **1.26M downloads/month**.

The mechanism, verified against `packages/core/src/testers/testers.ts`:

- `type Tester = (uischema, schema, context: TesterContext) => boolean`; `type RankedTester = (...) => number`. `TesterContext` carries `rootSchema` (for `$ref` resolution) and the form-wide `config`.
- `NOT_APPLICABLE = -1`.
- `rankWith(rank, tester)` returns a `RankedTester` that yields `rank` if the tester passes, else `NOT_APPLICABLE`.
- Primitives: `uiTypeIs(expected)` checks `uischema.type === expected`; `schemaTypeIs(expectedType)` resolves the sub-schema the control's `scope` points at and checks its `type`; `formatIs`, `scopeEndsWith`, `optionIs(name, value)`, `isControl` (truthy `uischema.scope`); combinators `and(...)` / `or(...)` fold over testers. Composites like `isBooleanControl` are `and(uiTypeIs('Control'), schemaTypeIs('boolean'), ...)`.
- Resolution (verified in `packages/react/src/JsonForms.tsx`): `maxBy(props.renderers, r => r.tester(uischema, schema, testerContext))` — **highest rank wins**; if the winner still returns `-1`, it renders `<UnknownRenderer type="renderer"/>`. The registry is a flat array mutated by `ADD_RENDERER`/`REMOVE_RENDERER`. Ties are resolved by lodash `maxBy` (first max wins) — undocumented and fragile.

This is the closest thing in the form world to a real capability-negotiation protocol: any predicate over (schema node, ui node, root schema, config) can bid, with a numeric priority.

**The maintainers themselves now describe the failure modes.** Issue #2571, "Presentation Model Approach Investigation", opened by maintainer `sdirix` on **2026-05-07**, states verbatim: "**Logic leaks into the 'UI' layer.** Required-label handling, visibility rules, enablement, error extraction, i18n key resolution, option computation, label derivation, path composition, etc., live in the mappers"; "**Customization is coarse-grained.** To customize cross-renderer functionality, e.g. change the 'label' computation, you often need to override every renderer"; "**Performance can be improved** Every form change re-runs all mappers." The proposed JSON Forms 4 direction replaces mappers with a centralized presentation model where "**Testers work against presentation nodes**" and which would let them "abstract over the JSON Schema, enabling an easier integration with JSON Schema less approaches" — i.e. the schema itself is being demoted. Experimental branch `feat/presentation-model`, demo at jsonforms-4-demo.netlify.app (comment 2026-06-12).

## react-jsonschema-form — shipped-and-adopted, healthy

15,875 stars; **v6.0.0 released 2025-10-31**, v6.8.0 2026-08-14; `@rjsf/core` **4.7M/month** — ~3.7× JSON Forms. Mozilla origin, now community-run (`rjsf-team`).

Widget selection, verified in `packages/utils/src/getWidget.tsx`: a hardcoded two-level table `widgetMap[schemaType][widgetName]` (e.g. `string.textarea → 'TextareaWidget'`, `string['data-url'] → 'FileWidget'`, `boolean.radio → 'RadioWidget'`). `ui:widget` may be a component directly (returned as-is), or a string looked up first in `registeredWidgets`, then in `widgetMap[type]`. Unknown combinations **throw**: `` `No widget '${widget}' for type '${type}' in schema` ``. No ranking, no predicates, no negotiation — a lookup table with a fixed key space. Extension means overriding by *name*, not by *capability*.

Known limits, evidenced by issues: #701 "Feature for embed UISchema into JSON Schema" (open since 2017, 86 reactions) — the two-document split is the single most-requested change; #1157 "Multiple pages proposal" (open since 2019) — no layout/wizard model; #3715 "Medium sized schema becomes uncomfortably laggy to type in inputs" (2023); #3692 "Terrible performance with big anyOf field"; #3517 "5.3.0: Array items perform much worse" (still open); #4567 "multiple accessibility issues" (open since 2025-04-16).

## Formily (Alibaba) — effectively dormant

12,566 stars but **last release v2.3.6 on 2025-05-15 and last push 2025-06-21** — 14 months stale as of today. `@formily/core` 145k/month (~3% of rjsf). Its model is genuinely different (a reactive field graph, MVVM, schema as one of several entry points), but issue and PR titles in the tracker are substantially in Chinese and I found no primary evidence of Western enterprise adoption. Grade: **shipped-niche, stalling**.

## Others, one line each

- **ngx-formly** (Angular): 2,966 stars, pushed 2026-08-17, 709k/month — the healthiest framework-specific one; field-type registry keyed by `type` string, same lookup-table limit as rjsf.
- **FormKit** (Vue, successor to Vue Formulate): 4,758 stars, pushed 2026-07-24, 734k/month — schema is a first-class rendering format, but it is FormKit's own schema, not JSON Schema.
- **Uniforms**: 2,104 stars, last push 2026-01-12, **no GitHub releases**, 88k/month — coasting.
- **SurveyJS**: 4,854 stars, 1.33M/month, pushed today — but **491 open issues**; commercially licensed; it is a survey engine, not a general UI generator.
- **AutoForm/shadcn**: derives forms from Zod rather than JSON Schema — the notable 2024-2026 shift is *TypeScript-schema-first* (Zod/Valibot/ArkType) over JSON-Schema-first. I have no adoption numbers verified.
- **Concise Encoding**: found no evidence of relevance to UI generation; skipping.

## Internal-tool builders

Repo vitality (2026-08-26): NocoDB 64,733★; ToolJet 40,766★ (1,165 open issues); Appsmith 40,748★ (**4,471 open issues**); Directus 37,467★; Refine 35,576★; Budibase 28,242★; Baserow 5,706★ (1,227 open issues).

The one I could verify mechanically is **Refine**, and it is instructive. `@refinedev/inferencer` inspects an API *response* (not a declared schema), infers field types, and generates React source rendered through `react-live`. Adoption: 57k/month against `@refinedev/core`'s 752k — **~7.5%**, i.e. it is scaffolding people run once and then abandon. And on **2026-08-25** an open issue was filed: "**Arbitrary code execution in @refinedev/inferencer via unescaped API field names reaching react-live**" (#7556). Runtime schema→UI generation is not just a fidelity problem; here it is a code-execution surface. Refine v5's documentation sidebar no longer lists Inferencer as a guide.

For Retool/Appsmith/Budibase/ToolJet/Directus/NocoDB/Baserow I could not obtain 2025-2026 primary evidence on their derivation mechanisms within this session. **UNVERIFIED** — treat my general knowledge (Directus generates a Data Studio from Postgres introspection; Retool generates a table/form from a query result; Budibase/NocoDB from table metadata) as unconfirmed here, and note that the ceiling claim ("fine until the first non-CRUD interaction, then you drop to custom components / custom JS") is a widely-repeated practitioner claim I did **not** verify against a citable 2025-2026 source.

## The honest verdict

The genuinely load-bearing finding is not a blog post — it is that **the maintainer of the most architecturally sophisticated system in this space wrote down, in 2026, that the abstraction leaks, that customization requires overriding every renderer, and that the answer is to abstract *away* from JSON Schema**. The "last 20% requires an escape hatch" is not folklore; rjsf's answer is "pass a component to `ui:widget`", JSON Forms' answer is "write a tester and outrank us", and both are admissions that the declarative layer ran out.

# (B) Component contracts as data — what's machine-readable, at which lifecycle stage

**DTCG — shipped, and it reached stable.** The **Design Tokens Format Module 2025.10**, "Final Community Group Report, 28 October 2025", published under the W3C Community Final Specification Agreement, states: "This document was published by the DTCG as a Candidate Recommendation… **This specification is considered stable.** Further updates will be provided in superseding specifications." (designtokens.org front page: "First stable version 2025.10 now available".) A companion **Resolver Module 2025.10** exists.

**Confirmed: it does not cover component APIs.** The full section list is Terminology / File format / Design token / Groups / Aliases / **Types** (color, dimension, fontFamily, fontWeight, duration, cubicBezier, number) / **Composite types** (strokeStyle, border, transition, shadow, gradient, typography). There is no notion of a component, a prop, a slot, or a variant anywhere in the document. DTCG standardized the *values* a design system passes around and deliberately did not touch the *interfaces* that consume them.

Tool support is real: **Style Dictionary v5.0.0 (2025-05-16)** made the DTCG reference syntax `{a.b.c}` non-configurable — "the opening, closing and separator characters are now set to be aligned with the DTCG spec" — and dropped `.value` suffix references; current v5.5.2 (2026-08-19), 8.1M downloads/month. DTCG's own adopter list names Figma, Framer, Penpot, Sketch, Supernova, Tokens Studio, Terrazzo, zeroheight, Knapsack.

**Figma — all of it is design-time or agent-time; none of it is app-runtime.**

- **Code Connect** is now at **v2.0.0 (2026-08-18)**, and it carries a hard deprecation: "**Framework-specific parsers will no longer receive updates or support. Template files are now the only actively maintained way of using Code Connect.**" Parser-based commands other than `migrate`/`unpublish` now exit with migration guidance. Templates are framework-agnostic snippet generators — which means Code Connect moved *away* from statically understanding React/Swift/Compose prop types and toward "run this template to produce a string". What it maps is Figma node → code component, plus prop-name/variant mapping; the artifact is a code snippet shown in Dev Mode, not a queryable type contract. Requires Organization/Enterprise plans. `@figma/code-connect` shows 4.8M downloads/month, though that number likely reflects CI installs rather than authors.
- **Figma MCP server** (2025→2026) is now remote-first. Its tool list includes `get_code_connect_map`, `add_code_connect_map`, `get_context_for_code_connect`, `get_variable_defs`, and — most relevant here — **`search_design_system`**: "Searches across all connected design libraries to find components, variables, and styles matching a text query. Returns matching assets so the agent can reuse existing design system elements rather than creating new ones." That is a *text* query over a *design* catalog, answered to an *agent* at authoring time. It is the closest thing Figma has to "which component fits this?" and it is neither typed nor runtime.
- **Figma is a public company** — SEC CIK 0001579878, file number 001-42761, 10-Q filed 2026-08-05. 2026 product direction is visibly AI-first: Figma Make ("prompt to code anything"), **Figma Weave** (AI workflows, now runnable from Claude/ChatGPT/Cursor via MCP as of 2026-08-11), Figma Sites (beta), Figma Buzz (beta), Figma Motion. Enterprise-managed MCP authorization went GA 2026-08-24.

**Custom Elements Manifest — the real machine-readable component contract, and it has stopped moving.** `schemaVersion` is **2.1.0, dated 2024-05-06**; the repo has exactly two tags (v2.0.0, v2.1.0) and its last substantive commit was 2024-10-02. The format is genuinely good: per-module `declarations` with `kind: "class"`, `customElement: true`, `tagName`, `members` (fields/methods with types), `attributes`, `events` with typed payloads, `slots`, `cssProperties`, `cssParts`, `superclass`, and discovery via a `"customElements"` field in `package.json`. `@custom-elements-manifest/analyzer` does 651k downloads/month — healthy — but it is a **build-time** generator.

**Storybook** — 90,937 stars, 10.5.10 stable (2026-08-20), 10.6 in alpha. **CSF Factories shipped**: `code/core/src/csf/csf-factories.ts` is in core, with per-renderer implementations (react, vue3, web-components, angular), a `csf-factories` codemod, and an automigration; `definePreview`/`defineMain`/`meta.story` appear throughout MIGRATION.md's Storybook 10 sections alongside CSF3, which remains supported. `@storybook/csf-plugin` was removed in 10.0. Storybook's contract data is `argTypes`, populated by **react-docgen** (78.8M/month) / react-docgen-typescript (66.5M/month) at build time and injected into the preview bundle. `react-docgen`'s enormous download count is misleading as an adoption signal for *contracts* — it is a transitive dependency of Storybook and CRA-lineage tooling.

**Web Types (JetBrains)** — 304 stars, schema last touched "update schema for 2024.2" (2024-05-14). **Frozen.** **VS Code custom data** — microsoft/vscode-custom-data, 240 stars. Both are IDE-autocomplete formats; both are typically *generated from* a CEM by a converter. Neither is queryable outside an editor.

**Web components in 2026.** Lit 21,788 stars, lit@3.3.3 (2026-05-14), 28.5M downloads/month — mature, slow-moving, not in decline. **Declarative Shadow DOM is done**: caniuse reports **94.27% global support** (Chrome 111+, Safari 16.4+, Firefox 123+). Active WHATWG work is on adjacent primitives — `scopedcustomelementregistry` global attribute (whatwg/html#12000, open, updated 2026-08-26), "Stream HTML into element or ShadowRoot" (#12758), module stylesheet `<link>` (#12339) — plus long-running WICG threads on open-stylable shadow roots (#909, 290 comments) and HTML Modules (#645, 199 comments). **Declarative Custom Elements has no live spec work**: the only DCE-titled item I could find in WICG/webcomponents is PR #1101 from 2025-04-18 ("Clarify that declarative custom element definitions don't contain declarative shadow roots"), still open. Grade: **research-prototype / stalled**.

# (C) THE KEY QUESTION — is a component's accepted-types contract queryable at runtime?

**Yes, in exactly one mainstream system, and in a scattering of niche ones. Nowhere in the mainstream component frameworks.**

The best answer by a wide margin is **WordPress Gutenberg's block registry** — and it answers your question almost word for word. Verified against `schemas/json/block.json` and `packages/blocks/README.md` on trunk:

- `block.json` declares `attributes` (each with a `type`), plus **containment contracts**: `parent` ("lets a block require that it is only available when nested within the specified blocks"), `ancestor` ("available inside the specified block types at any position of the ancestor block subtree"), `allowedBlocks` ("only the listed block types can be the children of this block"), and a context system (`providesContext`/`usesContext`).
- These are **registered into a runtime store** (`registerBlockType`) and read back with `getBlockTypes()` ("Returns all registered blocks"), `getBlockType(name)`, `getChildBlockNames()`, `hasBlockSupport()`.
- And critically: **`getPossibleBlockTransformations(blocks)` — "Returns an array of block types that the set of blocks received as argument can be transformed into."** Plus `getBlockTransforms('from'|'to')` and `findTransform(transforms, predicate)` — "returns the **highest-priority** transform where the predicate function returns a truthy value." `rawHandler({HTML})`/`pasteHandler()` run arbitrary HTML through that ranked predicate set to decide which blocks can render it.

That is structurally the same algorithm as JSON Forms' `maxBy(renderers, tester)` — a registry of predicates with priorities, queried at runtime against a piece of content — shipped at WordPress's scale.

Every candidate found, graded:

1. **WordPress Gutenberg block registry** — *shipped-and-adopted*. Types, containment, and a literal "what can render this?" query. The answer.
2. **JSON Forms ranked tester registry** — *shipped-niche*. `maxBy` over `RankedTester`s is a runtime lookup of "which renderer claims this node", but the contract is expressed as opaque predicates, not as inspectable data: you cannot enumerate what a renderer accepts, only ask it about one candidate at a time.
3. **Builder.io `registerComponent`** — *shipped-niche*, and the most literally "queryable": `ComponentInfo` carries `inputs: Input[]` (`name`, `type`, `required`, `subFields`), `canHaveChildren`, `models` (which content models may use it), and **`childRequirements` / `requiresParent`, each of which accepts "a MongoDB-style query (using sift.js) of what the children objects should match"** — e.g. `{'component.name': {$in: ['Button','Text']}}`. A component contract expressed as a *query*, evaluated at runtime.
4. **Plasmic `registerComponent`** — *shipped-niche*. `CodeComponentMeta.props` with `type: "slot", allowedComponents: [...]` (verified in `plasmicpkgs/chakra-ui/src/registerTabs.ts`): a runtime-registered containment contract naming exactly which components may fill a slot.
5. **Puck** (`@puckeditor/core`) — *shipped-niche*. `config.components[Name].fields` is a plain runtime object with typed fields; enumerable, but no accepted-content typing.
6. **Vue** — *shipped-and-adopted*, partially. `PropOptions` (`type: PropType<T>`, `required`, `default`, `validator`) survives into the runtime component object, so Vue is the one major framework where a component's declared prop types are genuinely introspectable at runtime — but "types" are JS constructors (`String`, `Number`), which carry no semantics about *content*.
7. **Angular `reflectComponentType()`** — *shipped-and-adopted*, weakly. Public API returning `ComponentMirror` with `inputs` (`propName`, `templateName`, `transform?`, `isSignal`), `outputs`, `ngContentSelectors`, `selector`. **Names only — no types.** You can ask what an input is called; you cannot ask what it accepts.
8. **Custom elements platform reflection** — *shipped-and-adopted*, weakly. `customElements.get(tag)` plus `static observedAttributes` and `formAssociated` are runtime-queryable, but yield attribute *names* only.
9. **Custom Elements Manifest consumed at runtime** — *shipped-niche, tiny*. It happens, but only in documentation viewers: `api-viewer-element` ("Based on Custom Elements Manifest format", 283 stars, **2,763 downloads/month**) fetches a CEM in the browser and renders a live API table; Storybook's web-components renderer has `src/docs/custom-elements.ts` which reads a CEM in the preview to build argTypes. Nothing routes *content* to *components* using it.
10. **Adaptive Cards** — *shipped-niche*. `CardObjectRegistry` with `findByName(typeName)` and `createInstance(typeName, targetVersion)`, plus a `GlobalRegistry` — a runtime type→element registry with version gating. Type-keyed dispatch, no accepted-content query.
11. **Figma MCP `search_design_system`** — *shipped*, but agent-time and untyped text search over a design catalog.
12. **MCP-UI** — *shipped, fast-growing* (5,103 stars; `@mcp-ui/client` 1.2M/month). Its remote-DOM mode has the host register a component set the server may address by name — a runtime host-side registry — but the contract is a name agreement, not a typed capability description. Worth watching; this is where the pressure to make "which component can render this?" answerable is now coming from.

And the strongest negative result: **React deleted its only runtime contract.** The React 19 upgrade guide, "Removed: `propTypes` and `defaultProps` for functions": "In React 19, we're removing the `propType` checks from the React package, and **using them will be silently ignored**." React's prop contracts now exist only in TypeScript types (erased at build) and in docgen JSON (build-time). The industry's dominant component model moved *away* from runtime introspectability during exactly the period when agents started needing it.

So: nobody has built a general one. The pattern exists and works — Gutenberg proves it at scale, Builder.io proves the query form, JSON Forms proves the ranked-predicate form — but every instance is welded to a single editor or CMS. There is no cross-ecosystem, framework-neutral answer to "which components can render this content?", and the one format that could have become it (CEM) has been frozen since May 2024 and is read only by doc viewers.
